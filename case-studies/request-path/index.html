The life of a request in the cloud

You type a URL and a page comes back. In between, the request crosses half a dozen systems, each configured in a different place and owned by a different team. This film follows one request through a typical AWS and Kubernetes setup, hop by hop, with the config that decides each step.

The stops

  1. DNSRoute 53 answers with an alias to the CDN.
  2. CDN edgeCloudFront ends TLS, upgrades HTTP to HTTPS and picks an origin by path.
  3. Load balancerAn ALB built from a Kubernetes Ingress. It only accepts traffic that came through the CDN.
  4. Gateway podsEnvoy pods of the service mesh receive the request and clean it up.
  5. Gateway + routesThe Gateway says which hosts it accepts. The VirtualService rules run top to bottom.
  6. The answerA rule matches and Envoy replies with the redirect itself. The browser follows it on a second trip.

What to take away

  • Every hop has its own config. DNS records, CDN behaviors, an Ingress, mesh objects. A change in one place only works if the layers before it send the request there.
  • Order matters twice. The CDN checks path behaviors in order, and so does the routing table. The first match wins.
  • Not every answer comes from an app. Redirects and rejections can come straight from the edge, the load balancer or the gateway.
  • YAML isn't the running config. The mesh control plane compiles it and pushes it to the gateway pods live.
  • Know who owns each layer. When something breaks, the first question is which layer answered.

Built from a real change. Hostnames, paths, repository and rule names, line numbers and header names are made up or changed, and some details are simplified. The architecture and the order of the hops are real.
